# Proxmox runtime backend integration

Use `ProxmoxBackend.from_env()` only when the explicitly selected runtime backend is `proxmox`. This backend has no local-Docker fallback. All Compose commands and Compose file writes run in the worker guest via QEMU guest agent (QGA); the API host never runs Docker or Compose.

Required runtime environment:

- `CR_PVE_URL=https://192.168.16.214:8006`
- `CR_PVE_TOKEN_ID=<PVE token identity>`
- `CR_PVE_TOKEN_SECRET=<PVE token secret>`

`CR_PVE_FINGERPRINT` may override the approved SHA-256 pin; when unset, the backend uses the approved pin `4dbfcdb1eb96af751c42d3c14e5a128a582fcff3e40b7149585fcc52619e05b7`. Pin verification runs in `HTTPSConnection.connect()` before HTTP headers, including Authorization, are sent.

Mode defaults to `probe`. Set `CR_PVE_MODE=dry-run` to record write plans without sending writes. Live writes require `CR_PVE_MODE=live`, `CR_PVE_LIVE_ENABLED=true`, and `CR_PVE_RESERVATION_DB` set to a non-empty absolute path for a shared SQLite database mounted at the same path in every API worker.

Optional fixed-target settings are `CR_PVE_NODE=pve4-bbf`, `CR_PVE_POOL=cr-range`, `CR_PVE_STORAGE=local-lvm`, `CR_PVE_BRIDGE=vmbr990`, and `CR_PVE_TEMPLATE_VMID=900000`. Bounds can be adjusted with `CR_PVE_REQUEST_TIMEOUT`, `CR_PVE_TASK_TIMEOUT`, `CR_PVE_TASK_POLL_INTERVAL`, `CR_PVE_MAX_TASK_POLLS`, `CR_PVE_MAX_RESPONSE_BYTES`, `CR_PVE_RESERVED_MEMORY_MIB`, `CR_PVE_POOL_MEMORY_MIB`, and `CR_PVE_DATASTORE_RESERVE_GIB`.

The FastAPI process must receive these variables explicitly at startup; it does not load the repository `.env` automatically. This module never prints credentials. Runtime ACLs need scoped PVE read access, `Pool.Audit`, clone/config/power/guest-agent and VM allocation rights on the approved pool, datastore, bridge, and read-only node audit path.

Integration interface:

- `preflight() -> dict`: read-only version, template ownership/state/hardware, pool, node and pool memory, VM quota, and storage checks.
- Preflight responses include `placement_target` with the configured PVE node, resource pool, template, worker VMID range, and fixed worker sizing. This is infrastructure placement metadata, not a physical room/rack location.
- `plan(scenario_id, compose_yaml, *, compose_sha256=None, attach_lab_network=False) -> dict`: candidate VMID and planned API calls; contains no Compose text.
- `up(scenario_id, compose_yaml, *, host_id="worker", attach_lab_network=False, compose_sha256=None) -> dict`: returns the worker `vmid` and digest; persist `(scenario_id, host_id, vmid, compose_sha256)` for later calls.
- `status(scenario_id, *, vmid, host_id="worker") -> dict` and `down(...) -> dict`: require that persisted identity and revalidate pool membership, tags, and JSON description before guest or destructive actions.
- Status responses include the owned worker's `placement` (node, pool, VMID/name/state, configured vCPU/memory/disk, and NIC count); the scenario deployment status API carries this to the UI.
- `guest_exec(scenario_id, *, vmid, host_id, command, timeout=60, require_isolation=True) -> dict`: bounded public QGA command interface requiring the matching active durable reservation and a passing isolation report by default.
- `start_probe_operation(...)`, `wait_probe_operation(...)`, `cancel_probe_operation(...)`, and `join_probe_operation(...)`: bounded operation API for the pinned PoC helper. Each operation uses a unique 32-character random ID and is bound to the active scenario, service, worker VMID, and host.

At deployment time the backend generates a throwaway database password in memory, writes the Compose interpolation values to `/opt/cr-runtime/compose.env` inside the zero-NIC worker, and restricts the file to mode `0600` before running Compose. Every Compose command, including service execs, uses that env file. The password is not stored in the API database or request journal; removing the worker removes the file. Failed `up` responses include a bounded, redacted guest diagnostic to make startup errors actionable. The deployed reset snapshot also contains this throwaway value; it must never be replaced with a real external credential.

The guest Compose project name is `cr-demo-<scenario_id>`, matching the existing `manager.project_name` contract. PVE VM names map scenario-ID underscores to hyphens to satisfy the PVE DNS-name rule; ownership metadata keeps the original scenario ID. Host-only `cr-gateway` and `edge` are removed during PVE normalization, and all service `ports` host mappings are stripped; PVE does not publish host ports, while container `expose` declarations and internal network attachments remain. PVE workers always have zero NICs, and `attach_lab_network=True` is rejected. Any network without the default/omitted `bridge` driver, `internal: true`, and exact `driver_opts: {com.docker.network.bridge.gateway_mode_ipv4: isolated}` is rejected. Isolation reporting also requires Docker inspect `Driver=bridge`. The only supported Compose build uses the fixed context `../../templates/demo-app`, `Dockerfile`, and `pull: false`, plus a generated `container_name` of `cr-demo-<scenario_id>-<host_id>` and matching image `<container_name>:local`; it is rewritten to `./demo-app`, and the fixed repository `Dockerfile` and `server.py` are sent to `/opt/cr-runtime/demo-app` via QGA. Other build identities, services, contexts, Dockerfiles, and build options fail before clone. Each QGA file write is capped at 60,000 UTF-8 bytes. Before `up` succeeds, the guest's normalized Compose network names, Docker `Internal`, and Docker `Options` are checked through QGA; missing or mismatched isolation evidence triggers owned cleanup. Up/down operations serialize placement and destruction with an exclusive SQLite lock and one durable reservation row per worker VMID (table `pve_worker_reservations`, primary key `vmid`, unique `(scenario_id, host_id)`). A row is committed before clone, retained while the worker exists, and removed only after successful down or verified cleanup. Placement is refused when the table already holds `MAX_WORKER_VMS` rows, when the same scenario host already holds a row, or when any row is not `active`: a process crash leaves its row in `creating`, `deleting`, or `reconcile` state and blocks all further placement pending manual reconciliation. `down` and public `guest_exec` require the active row for their exact VMID. The pre-2026-11-15 singleton table `pve_worker_reservation` (`CHECK(slot = 1)`) is migrated automatically: under the exclusive lock its row is copied into the per-VMID table and the old table is dropped in the same transaction. **Operational requirement:** this migration assumes a single schema version writes the reservation database. Before starting the new code, drain and stop every old API process/container that mounts `CR_PVE_RESERVATION_DB`; do not run a rolling or mixed-version deployment during the migration, because old code recreates and writes the singleton table and does not see the per-VMID table. In live mode, every API worker/container must mount the same `CR_PVE_RESERVATION_DB` path; live mode fails closed if the variable is absent. Failed clone/config steps return a recoverable reconciliation record when an exact provisional clone cannot safely be removed.

The Linux template is fixed at VMID 900000 with exactly `scsi0` (20 GiB) and `ide2=local-lvm:vm-900000-cloudinit,media=cdrom`. Worker VMIDs are 900100–900999. At most `MAX_WORKER_VMS = 5` worker VMs may exist in the worker range at a time (product-owner approval on 2026-11-16 supersedes the prior cap of 2; preflight counts every pool member ≥ 900100, running or stopped, and the reservation table enforces the same cap). This is a hard ceiling, not a capacity guarantee. The current `cr-range` memory budget is 16384 MiB and includes the 4096 MiB template; with workers fixed at 4096 MiB each, this budget can hold **at most 3 worker VMs** (template 4 GiB + workers 12 GiB). To fit five workers under the pool budget, it must be at least 24576 MiB, and each placement must still pass the node free memory ≥ 3072 MiB reserve + 4096 MiB check. No node/pool limits or per-worker sizing are raised by the cap change. Storage must remain above the 40 GiB reserve + 20 GiB worker disk; node memory and storage may lower the practical limit further. The pool also allows at most `MAX_WORKER_VMS` running worker VMs. Each worker is fixed at 2 vCPU and 4096 MiB; the node must also retain the configured 3072 MiB reserve. QGA Compose file writes are limited to 60,000 UTF-8 bytes (below PVE's 61,440 character ceiling). The worker template has no NIC, and the backend never adds one.

## Cancellable PoC operation lifecycle

The deployed guest receives the fixed `/opt/cr-runtime/probe-supervisor.sh` through the allowlisted QGA file-write path. It keeps an operation journal and per-operation `flock` under `/var/lib/cr-runtime/probe-operations`; state changes are synced before a helper may launch. The helper container name and labels use the random operation ID. Before removing it, the supervisor verifies its operation/scenario/target labels, pinned image, exact target network mode, unprivileged user, read-only root, dropped capabilities, and CPU/memory/process limits, then removes by the inspected container ID and confirms that ID is absent.

The shared `CR_PVE_RESERVATION_DB` gives each worker reservation a unique generation ID, retained through its lifecycle and replaced on redeployment even when PVE reuses the same VMID. The successful deployment record carries this ID, and each POC job captures the recorded worker identity before its actions run. Before a job stores an operation ID or can request a launch, the backend commits a `reserved` row to `pve_probe_operations` under the same exclusive placement lock used by `down` and `reset`; `reserved`, `starting`, `running`, `cancel_requested`, and `uncertain` rows block those lifecycle transitions. The operation row and job then carry the exact scenario, host, VMID, generation ID, and operation ID. `start`, `wait`, `cancel`, and `join` require this identity and never resolve a replacement worker from the scenario ID. The row is retained until terminal guest state and resource absence are confirmed. Terminal IDs remain as tombstones after worker removal so an old delayed start cannot reuse an operation ID on a later worker. A cancel request commits its host-side fence before QGA cleanup. Guest-side tombstones make a later start with that operation ID fail. Start and cancellation are serialized by both the shared reservation lock and the guest's per-operation lock. If QGA or Docker state cannot be confirmed, the operation stays `uncertain`, the PoC job remains available for a later cancel retry, and worker cleanup/reuse fails closed. Cancellation also scans durable PVE reservations so a process crash between creating the reservation and attaching it to its POC job can be reconciled. A successful cancel response means the exact helper is absent; `joined` reports terminal confirmation. A request that returns `uncertain` requires reconciliation before that worker can be stopped or reused.

Vulnerable PoC execution still refuses `local-docker` under D6. This host-side ledger and harmless local supervisor test suite do not verify live QGA, the deployed Debian template's `flock`/Docker behavior, or the PVE lifecycle. Validate those separately against the authorized PVE worker before enabling live PoC execution.

Live smoke verification was completed on 2026-11-15 against PVE 9.2.2 using the approved synthetic `scn_2acb1b9c902c` scenario. The official API created worker VMID 900100, started its two preloaded services inside the zero-NIC guest, confirmed the guest network isolation evidence, then `/down` removed the Compose resources and VM. The candidate Deploy UI showed the PVE target and zero-NIC notice; its Start/Stop buttons completed the same real lifecycle. A post-cleanup preflight reported zero worker VMs and the shared reservation table was empty. This verifies one internal deployment lifecycle only; it does not validate concurrent API workers, external client access, vulnerable-image deployment/probes, or production operations. Keep live mode explicitly gated and retain manual reconciliation for uncertain clone outcomes.
