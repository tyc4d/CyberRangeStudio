# 模組 1 設計比較（Lead 整理，2026-11-14）

來源：`analysis-claude.md`、`analysis-codex.md`（兩個 Worker 各自獨立分析）。
狀態：**建議案，等產品負責人確認。尚未核准開發。**

## 三種做法

| | 做法 | 最大優點 | 最大缺點 |
|---|---|---|---|
| 一 | 一次問完：整份丟給 LLM，直接產出 JSON | 最快做出來 | 漏了、編了都看不出來，缺少項目清單不可信 |
| 二 | 全部先轉成 STIX 再分析 | 內部只有一種格式 | STIX 放不下攻擊步驟與先後順序，轉一次掉一次（研究有實測） |
| 三 | 分段處理：程式讀 STIX 與切段編號，LLM 只抽有出處的內容，程式核對引文 | 每一項都能追回原文，錯在哪一步查得到 | 步驟多，第一版較費工、費用較高 |

另有「人主導、LLM 只提候選」的做法，正確性最高但最慢，離自動化目標最遠；
建議只借用它的「人工確認」當初期保險。

## 兩個 Worker 的共識

- 都建議做法三。
- STIX 裡確定的欄位由程式直接讀，不經 LLM。
- 「NULL」不夠用，要區分：報告沒寫、模糊、不適用、推測、互相矛盾、解析失敗。
- `related-to` 不能當成攻擊先後順序。
- 「JSON 有效」「引文存在」都不等於內容正確；引文是否真的支持結論需要人工或另一層檢查。
- 品質評估不給單一總分，給算得出來的分項數字。
- 草圖的「確認 XML 格式」只適用 STIX 1.x；STIX 2.x 是 JSON。
- 先前研究從未成功呼叫 LLM，「原文好還是 STIX 好」沒有數據。

## 兩者的差異

| 議題 | Claude | Codex | Lead 看法 |
|---|---|---|---|
| 第一版是否含 STIX 1.x | 先不做 | 要做 | 屬產品決定，問產品負責人 |
| 缺少項目怎麼算 | 對照「建環境必備清單」由程式算 | 用欄位狀態標示 | 兩者都要；必備清單需和模組 4～6 一起定 |
| LLM 用自身記憶補資料 | 明確禁止，外部知識留給模組 2 | 標成「推論」 | 屬產品決定 |

## Claude 另外指出、Lead 認為重要的風險

- 只有 IOC 的 STIX 抽不出攻擊流程，應回報「資料不足」而非讓 LLM 補故事。
- 測試用的 3 份報告都是知名事件，LLM 可能背過，會高估能力；需加入較新或冷門的報告。
- 報告是不可信輸入，內容可能夾帶指令。
- 一份報告不一定是一條攻擊鏈。
