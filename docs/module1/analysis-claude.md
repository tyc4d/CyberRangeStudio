# 模組 1「情資報告分析」設計分析（Claude Worker）

只做設計分析，沒有寫產品程式，沒有跑任何測試、安裝或付費 API。
依據：`docs/product-questions.md` 與 `~/cr-research-m1/research` 的兩份研究（只當參考）。

## 0. 先說研究能信多少

**可以相信的（有實測）**
- 格式正確的 STIX 不等於內容夠用。現成轉換工具（純規則比對，沒用 LLM）只抓得到 IOC，
  25 個攻擊行為、21 條先後關係一個都沒抓到；產生的關係全是沒有方向的 `related-to`。
- STIX 1.x 轉 2.1、2.0 轉 2.1 都能跑，但轉完仍可能驗證不過，原本的錯不會被修好，部分標籤會掉。
- 同一份報告包成 STIX 後，輸入量是原文的 1.6～6 倍。

**證據弱、不能當結論的**
- **從頭到尾沒有成功呼叫過任何 LLM**。「LLM 讀原文好還是讀 STIX 好」完全沒有數據。
  兩份研究的建議還互相矛盾（一份說 STIX＋原文，一份說原文為主），兩者都只是工程判斷。
- 「0/25、0/21」量的是規則式工具，不能說明 LLM 做得到或做不到。
- 參考答案只有 3 份報告、1 個人整理、沒人複核，行為切多細也還有爭議。
- 3 份都是知名公開事件，LLM 很可能早就「背過」，拿來測會高估能力。
- 測的 STIX 是從原文轉出來的，裡面塞了全文。真實拿到的 STIX 多半只有 IOC、沒有敘述，
  所以「STIX 裡什麼都有」這個觀察不能套用到真實輸入。STIX 1.x 只測了 1 份官方範例檔。

## 1. 四種可行做法

### 做法 A：一次問完
所有輸入（STIX 也攤平成文字）整份交給 LLM，一次輸出六大類 JSON，再用程式檢查格式與引文。
- 優：最簡單、最快做出來；LLM 一次看到全文，前後文關係不會被切斷。
- 優：成本好估，一份報告一次呼叫。
- 缺：長報告容易漏項，而且漏了沒有任何訊號，「缺少項目」會不準。
- 缺：哪一類出錯無法單獨重跑或調整；STIX 裡本來就確定的欄位也交給 LLM 重抄，平白多出抄錯機會。
- 缺：品質評估只能靠 LLM 自評，不可靠。

### 做法 B：分段處理，程式與 LLM 各做擅長的事
1. 程式先整理輸入：原文切成有編號的段落；STIX 用程式直接讀出確定的欄位（IOC、CVE、工具名），來源記為「哪個物件的哪個欄位」。
2. LLM 分幾步抽取：先抽攻擊行為，再抽關係、目標環境、工具與指令，每一項都要附段落編號與原句。
3. 程式核對引文：原句是否真的在該段落裡。再抽查「這句話是否真的支持這個結論」（第二次 LLM 或人工）。
4. 缺少項目由程式對照一份「建環境必備欄位清單」算出來，不由 LLM 自己說。
- 優：STIX 的確定資料不經 LLM，不會被改錯；引文可由程式查核，幻覺抓得到。
- 優：缺少項目與品質分數是算出來的，可重現、可解釋；每一步能單獨量品質、單獨改。
- 缺：步驟多，第一版工時較長，呼叫次數與費用較高。
- 缺：分步後，後面步驟會繼承前面的錯（行為抽錯，關係跟著錯）。
- 缺：「必備欄位清單」需要先定義，這其實取決於模組 4～6 要什麼，現在還沒定。

### 做法 C：全部先轉成 STIX 2.1，再從 STIX 產生 JSON
原文先用工具或 LLM 轉成 STIX，STIX 1.x 用官方工具升級，內部只認 STIX 2.1。
- 優：內部只有一種格式；可與其他情資平台交換、去重。
- 缺：STIX 沒有地方好好放「具體攻擊步驟、先後順序、目標機器的版本與設定」，這正是建環境最需要的。
- 缺：原文轉 STIX 這一步研究已實測會丟掉行為鏈；多一次轉換就多一次遺失，引文也更難對回原文。
- 缺：等於要自己擴充 STIX，互通的好處大半消失。

### 做法 D：人主導，LLM 只提候選
LLM 在原文上標出候選項目，分析師逐項確認或修改後才寫入 JSON。
- 優：正確性最高，每一項都有人負責；適合品質還沒量過的初期。
- 缺：每份報告都要專業人力，速度慢，與「自動生成」目標距離最遠。
- 缺：需要操作介面，第一版範圍變大；而且流程後面已有「人工確認」，可能重複。

## 2. 對產品負責人流程草圖的看法

**合理的部分**
- 六大類資訊切得對，正好是後面建環境需要的（做什麼、先後、打誰、用什麼、依據在哪）。
- 要求引用段落、標記拿不到的資訊、驗證 evidence，方向正確，是防幻覺最有效的手段。
- 輸出同時給 JSON、缺少項目、品質評估，讓模組 2 與人工確認有東西可接。

**有風險或缺漏的部分**
1. **「STIX Parser 確認 XML 格式」只對 STIX 1.x 成立**。STIX 2.x 是 JSON。兩者要分開處理；1.x 轉換會掉資料、轉完可能驗證不過，需決定「轉換有錯時怎麼辦」。
2. **只有 IOC 的 STIX 抽不出攻擊流程**。草圖沒說這種輸入要怎麼處理。該明確回報「資料不足以建環境」，而不是讓 LLM 補故事。另外 STIX 沒有「段落」可引用，引用方式要另訂（物件與欄位）。
3. **「NULL」太粗**。至少要分：報告沒寫、報告寫了但模糊、不適用、是推測不是原文。模組 2 要靠這個判斷該補什麼。
4. **「缺少」要有對照標準**。沒有「建環境必備欄位清單」，就無法定義什麼叫缺。這份清單要和模組 4～6 一起定。
5. **引文存在 ≠ 引文支持結論**。程式只能確認原句存在；「這句話能不能推出這個結論」要另一層檢查。
6. **LLM 會用自己記得的知識補資料**（例如報告沒寫版本，它卻填了）。看起來正確，但不是報告說的。要明確規定：模組 1 只收報告裡有的；外部知識屬於模組 2，且要標明來源。
7. **Schema Validator 只檢查格式，不檢查內容對不對**。不能把「JSON 有效」當成品質。
8. **「生成品質評估」沒說怎麼算**。若由 LLM 自己打分，沒有參考價值。應由可計算的數字組成：引文通過率、必備欄位填寫率、未驗證項目數、推測項目數。
9. **缺原文前處理**。PDF/網頁轉文字時表格、圖片裡的指令、頁碼會掉；報告常把 IOC 寫成 `hxxp`、`1.2.3[.]4`。前處理沒做好，後面的引用全部對不上。
10. **報告是不可信輸入**。內容可能夾帶「忽略先前指示」之類的字句，也含真實惡意網址與樣本資訊，需當資料處理，不當指令。
11. **一份報告不一定是一條攻擊鏈**。例如 CISA 的報告是多起入侵的綜合描述，不是單一時間線。攻擊手法清單（ATT&CK 表）也不等於實際發生的步驟。草圖沒有處理「順序不明」的情況。
12. **沒提結果穩定性**。同一份報告跑兩次結果可能不同，後面模組會受影響，需要量測與記錄版本。

## 3. 建議

**建議採做法 B**，並在品質量出來之前，借用做法 D 的「人工確認」當保險（放在模組 1 輸出之後，不必做專用介面，先看報表即可）。

理由：
- 最終目標是「能說清楚哪些被重現、依據是什麼」。這要求每一項都能追回原文，只有 B 把「可查核」做進流程。
- 研究唯一確定的事是「STIX 當唯一格式不夠用」，排除 C。A 做得快，但漏項與幻覺都看不到，缺少項目清單不可信，而那正是模組 2 的輸入。
- B 的每一步可以單獨量，之後換模型、改提示時知道是變好還是變壞。

**最小可用的第一版**
- 輸入：已是文字的原文報告（網頁、有文字層的 PDF）＋ STIX 2.1。STIX 1.x 與掃描檔先不做（見第 4 節問題 1）。
- 原文：切段編號 → LLM 抽「攻擊行為、目標環境、工具與指令」三類，逐項附段落編號與原句 → 程式核對原句存在，對不上的項目標為「未驗證」而不是刪掉。
- STIX 2.1：程式直接讀 IOC、漏洞、工具等確定欄位，不經 LLM；若沒有敘述文字，直接回報「無攻擊流程資料」。
- 關係（先後順序）第一版只收原文明講的，其餘標「順序不明」。
- 缺少項目：對照一份很短的初版必備清單（例如每個行為要有：目標系統、所需權限、用到的工具或指令；每個目標要有：作業系統、服務、版本）。
- 品質評估：只給算得出來的數字，不給單一總分。

**品質怎麼量**
- 先補測試資料：現有 3 份報告的參考答案請第二個人複核；再加 2～3 份較新或較冷門的報告，降低 LLM「背過」的影響。
- 抓到多少、抓錯多少：與人工參考答案比對，由人判定是否算同一項（不交給 LLM 判）。
- **沒有依據的項目數**（最重要）：有幾項在原文找不到支持。
- 引文：原句存在率（程式算）、原句是否真的支持結論（人工抽查）。
- 刪除測試：把報告某段拿掉再跑一次，該項應變成「缺少」。若仍被填上，表示 LLM 在用自己的記憶。
- 穩定性：同一份跑 3 次，結果差多少。
- 每份報告的時間與費用。
- 實用性：請一個人只看 JSON、不看原報告，試著寫出環境需求，記錄卡在哪裡。

## 4. 只有產品負責人能回答的問題

1. STIX 1.x 第一版就要支援嗎？手上有真實的 STIX 1.x、2.x 檔案可當樣本嗎？它們通常含敘述文字，還是只有 IOC？
2. 輸入只有 IOC、沒有攻擊過程時：直接拒絕、還是照做並列出一大串缺少項目？
3. 模組 1 可不可以用報告以外的知識（例如由 CVE 推出受影響版本、對應 ATT&CK 編號）？還是一律留給模組 2？
4. 模組 1 做完後，要不要有人先看過才進模組 2？看的人具備什麼程度的資安背景？
5. 報告的語言與形式：只有英文嗎？會有中文、掃描檔、截圖裡的指令嗎？
6. 報告能不能送到外部雲端 LLM？有沒有機密或限制散布的情資必須留在本機處理？
7. 一份報告講多起事件，或多份報告講同一事件時，期望是一個場景還是多個？
8. 寧可漏掉（只收有把握的），還是寧可多列（不確定的也列出並標記）？
9. 「品質評估」給誰看、用來決定什麼？是給使用者一個「可不可以往下走」的燈號，還是給分析師看的明細？
10. 每份報告可接受的處理時間與費用上限大約多少？
