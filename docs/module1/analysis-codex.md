# 模組 1「情資報告分析」設計分析

## 可行做法

### A. 依輸入格式分流，再合併成共同 JSON
- STIX 1.x / 2.x 先用格式專用解析器讀物件、欄位和關係；原始 XML/JSON 與來源定位一併保留。原始報告則抽成可定位的段落，再由模型擷取敘述中的行為和環境資訊。
- 優點：已明確寫在 STIX 的欄位不必重新猜；原報告仍可補足 STIX 沒有的行為細節。
- 優點：能指出解析失敗或版本轉換造成的損失，便於後續追查。
- 缺點：不同 STIX 版本與自訂欄位需要維護對照；版本轉換不保證語意完整。
- 缺點：來源同時附原文和 STIX 時要去重，並處理兩者矛盾。

### B. 單次模型讀完整輸入並產生 JSON
- 原始報告直接輸入；STIX 則連同 Bundle/物件文字交給模型，要求填完整 schema、引用原文或物件欄位。
- 優點：流程短，容易先做出端到端樣品；格式多變的報告可用同一套擷取規則。
- 優點：不必先寫大量欄位對照，可快速觀察輸出形狀是否符合下游需要。
- 缺點：長文或大型 Bundle 容易漏步驟、混淆 IOC 與攻擊行為，單次輸出也難定位錯在哪。
- 缺點：JSON 合法、引用文字存在，都不能證明引用支持該主張；模型可能把推測寫成事實。

### C. 先建證據索引，再分段抽取、合併和核對
- 先解析文件或 STIX，給每段原文、每個 STIX 欄位穩定來源 ID；模型逐段抽成原子主張及引用，再合併重複項、整理關係並產生共同 JSON。
- 優點：每個主張可回到精確段落、頁碼或 STIX 路徑；可自動檢查來源 ID、定位點和引文是否存在。
- 優點：分開檢查行為、目標、Artifact 和關係，較容易找到漏項或不受支持的說法。
- 優點：缺失與衝突可保留為明確狀態，不必用空值掩蓋差異。
- 缺點：比單次擷取多了切段、去重、關係合併等環節，整合與維護較費工。
- 缺點：切段可能拆散跨段因果；引用存在的自動檢查仍不能判斷語意是否支持主張。

## 對產品負責人流程草圖的看法

**合理處**
- 同時考慮 Raw CTI、STIX 1.x 和 STIX 2.x，並把 parser、模型分析、schema 驗證分開，是可檢查的起點。
- 六類資訊涵蓋下游建場景會用到的事件、行為、目標、工具/IOC、關係和來源。
- 要求證據、缺失標記和 JSON 驗證，符合「結果供後續模組使用」的要求。

**風險或待補處**
- 只確認 STIX 1.x 的 XML 格式不足以確認 STIX 語意有效；STIX 2.x 是 JSON，還要檢查版本、物件型別、引用與關係端點。轉成另一版也可能遺失欄位。
- 所有缺欄都填 NULL 會混淆「報告沒提到」、「未知」、「不適用」、「來源互相矛盾」和「解析失敗」。要保留不同狀態及原始輸入。
- STIX 的 `related-to` 或 IOC 關聯不代表攻擊先後。攻擊步驟、時間順序、因果/依賴、ATT&CK 技術標籤應分開記錄，不能互相替代。
- 證據應附在每一個原子主張上，包含來源識別、精確引文與頁/段/欄位定位；驗證引用字串存在不等於驗證語意支持，後者需人工審核或另有明確評分規則。
- Schema Validator 只能驗結構。還需定義跨欄位檢查、解析警告、推論/不確定標記，以及品質評估各維度；避免只給一個看似精確的總分。
- Target Context 要區分報告明載和推論，尤其不能由漏洞或工具名稱直接推定受害主機版本/拓樸。輸出需有來源、信心或「未確認」狀態。

## 建議與最小可用版本

建議以 **C 為主、A 的格式分流為底**：解析器負責 STIX 結構與來源定位；原始報告建立可定位文字；模型只抽取有來源根據的主張，並整理成共同 JSON。保留原始輸入及雜湊。每個欄位明確標出 `observed / inferred / unknown / not_applicable / conflicting / parse_error` 等狀態；證據引用包含來源 ID、原文位置和短引文。一般 `related-to` 不得轉成攻擊順序。自動核對格式、必填欄位、來源 ID/定位與引文存在；引用是否支持主張仍列為待審，不宣稱自動驗真。

第一版支援純文字報告輸入及 STIX 1.x XML、STIX 2.x JSON；只輸出事件摘要、攻擊行為、方向明確且有證據的關係、目標環境、工具/IOC、缺失清單、來源引用和分項品質狀態。對 PDF/HTML/掃描件的檔案支援與語言範圍先由產品負責人定義，再決定納入哪種原文擷取；解析不完整時回報警告，不靜默丟棄。

品質用小型、人工雙重複核且涵蓋三種輸入路徑的案例集衡量。分別看：JSON/格式解析通過率；攻擊行為與各類關係的 precision/recall；引用定位正確率及人工判斷的主張支持率；Target/Artifact 正確率；缺失項目召回及誤報率；不受支持主張比例。按輸入種類分開報告，並把重複執行差異列出；結構有效不代表分析品質達標。門檻由產品負責人訂定。

## 研究依據與限制

- `cti-to-stix` 研究以三份報告比較工具；暫定清單標出 25 個行為、21 條順序/依賴邊，但尚無第二位分析師複核，部分行為切分也待裁定。pattern-only 工具未保留這些結構化行為/邊，不能據此評斷 LLM。
- 研究中有 STIX Bundle 通過 Validator，也有 API 物件包成 Bundle 後驗證失敗；兩者只說明特定輸出格式狀況，不代表分析完整度或所有部署版本表現。
- `cti-input-benchmark` 的 A/B/C 模型呼叫因缺授權金鑰而未送出，沒有模型品質、成本或延遲比較。離線 token 預估不是供應商實測；B 的三個 Bundle 已含全文，C 另帶原文會重複輸入。
- STIX 1.x/2.0 相容性只用有限 fixture；研究結果可提示轉換風險，不能當成各版本、各來源的完整覆蓋證明。
- 主要參考：`cti-to-stix/README.md`、`reports/research_report.md`、`reports/recommendation.md`、`results/comparison.csv`、`results/failed_cases.md`；`cti-input-benchmark/README.md`、`reports/benchmark_report.md`、`reports/reference_check_audit.md`、`results/benchmark.json`、`results/performance.csv`。
